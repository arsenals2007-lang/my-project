# Памятка для защиты варианта 18

## Что сказать о программе

«Это консольный эмулятор командной оболочки на Python. Приглашение берет
имя пользователя и имя компьютера из ОС. Команды работают с виртуальной
файловой системой, загруженной из XML. Содержимое файлов, каталоги и
владельцы хранятся в памяти; изменения не затрагивают исходный XML.
Работа выполнена последовательно в пяти этапах с отдельными коммитами
и тегами».

Показывать файл README и текущую программу из корня проекта.
Проверка перед защитой: `make test`.

## Архитектура

1. `__main__.py`: `argparse` читает настройки, `VFS.load` загружает XML,
   `run_script` выполняет начальные команды, затем запускается REPL.
2. `parser.py`: посимвольный `Lexer` хранит тип кавычек и буфер аргумента.
   `parse_command` возвращает список токенов, раскрывая переменные ОС.
3. `shell.py`: `Shell` хранит `cwd`, предыдущий каталог, признак работы,
   объект VFS и словарь обработчиков. `execute` находит команду в словаре;
   ошибки `ValueError` превращаются в сообщение без завершения REPL.
4. `vfs.py`: словарь `{абсолютный_путь: Node}`. `Node` содержит тип узла,
   байты, владельца и группу. `resolve` проверяет компоненты пути,
   `children` возвращает прямых отсортированных потомков.
5. `commands.py`: основные команды. `tree` вызывает
   `print_tree`, который обходит дерево через явный стек; `cal` использует стандартный модуль `calendar`.
6. `mutations.py`: `mkdir` добавляет `Node`, `chown` меняет метаданные.
   Общие проверки флагов и числа аргументов вынесены в `options.py`.

## Живая демонстрация

### 1. История этапов

```sh
git log --oneline --decorate
git tag --list 'stage-*'
git show stage-1:src/shell18/shell.py
git show stage-2:src/shell18/__main__.py
git show stage-3:src/shell18/vfs.py
```

`git show` показывает сохраненный код без переключения и изменения
рабочего каталога. На этапе 1 `ls`/`cd` были заглушками; в итоговой версии
они работают с VFS. Теги `stage-4` и `stage-5` добавляют основные и
дополнительные команды соответственно.

### 2. Конфигурация и источники

```sh
sh run.sh --help
sh scripts/test_config.sh
sh scripts/test_vfs.sh
```

Показать `examples/minimal.xml`, `files.xml`, `deep.xml`.
В `files.xml` файл `binary.bin` закодирован base64; в `deep.xml` путь
`/home/student/projects/demo` демонстрирует четыре уровня каталогов.
Ошибки `invalid.xml` и отсутствующего файла здесь ожидаемы: сценарий
проверяет их и в результате должен вернуть 0.

### 3. Интерактивный сеанс

```sh
sh run.sh --vfs examples/deep.xml
```

После запуска вводить команды по одной:

```text
pwd
ls
ls -al
tree -a
cd "/folder with spaces"
pwd
cd /
cd /home/student/projects/demo
ls -l
cd ..
cd -
cal 2 2024
mkdir -p /work/a/b
chown -R alice:staff /work
ls -l /work
ls -l /work/a
mkdir -- -dash
ls -a
unknown
cd /etc/config.txt
ls "unfinished
pwd
exit
```

Объяснить: скрытый файл виден только с `-a`; `cd -` возвращает предыдущий
путь; в феврале 2024 года 29 дней; `mkdir` и `chown` меняют VFS;
ошибки не препятствуют следующему `pwd`. Приглашение обновляет путь.

Для парсера запустить отдельный сеанс с переменной реальной ОС:

```sh
DEMO=/etc sh run.sh --vfs examples/deep.xml
```

Ввести `ls $DEMO`, затем `ls '$DEMO'`, затем `exit`. В первом случае
парсер подставит `/etc`; во втором будет искать буквальный путь `$DEMO`
и выдаст ожидаемую ошибку. Кавычки и комментарии не передаются команде.

### 4. Стартовые сценарии и коды завершения

```sh
sh run.sh --vfs examples/deep.xml --script examples/demo.shell --batch
```

Успешный пример должен завершиться кодом 0. Затем:

```sh
sh run.sh --vfs examples/deep.xml --script examples/stage5.shell --batch
```

В этом примере ошибки намеренные. Показать номер строки в сообщении и
успешный `pwd` после ошибочных команд. Код завершения 1 ожидаем;
сценарий `scripts/test_commands.sh` проверяет именно такое поведение.
Аналогично `stage4.shell` проверяет режимы основных команд.

### 5. Изменения существуют только в памяти

Перезапустить `sh run.sh --vfs examples/deep.xml` и ввести `ls /work`:
каталог, созданный в предыдущем сеансе, отсутствует. Исходный XML
не содержит этого каталога. В тесте `test_only_memory_changes`
сравниваются исходные байты XML и содержимое реальной папки до/после
команд, затем VFS загружается снова.

```sh
make test
sh scripts/test_commands.sh
```

Тесты проверяют не только успешные примеры, но и ошибки формата, путей,
опций, работу кавычек, base64, календаря и отсутствие записи на диск.

## Частые вопросы

**Почему XML?** Он требуется вариантом 18 и позволяет представить
вложенные каталоги, текстовые данные и метаданные. Двоичные данные
передаются через base64 и после загрузки хранятся как `bytes`.

**Где хранятся реальные файлы из VFS?** Они не создаются на диске.
Есть только узлы в `VFS.nodes`; XML используется как входной источник.

**Как работает относительный путь?** Начальная точка - `Shell.cwd`.
Компоненты проверяются последовательно; `.` сохраняет текущий каталог,
`..` поднимает к родителю, а в корне оставляет `/`.

**Почему нельзя просто нормализовать путь?** Нормализация могла бы
скрыть ошибку, например пройти через файл в пути `file/..`.
`walk_component` проверяет, что каждый промежуточный узел - каталог.

**Почему `$HOME` иногда дает ошибку?** Это переменная реальной ОС,
но путь команды ищется в VFS. Наличие такого каталога в реальной ОС
не означает его наличие в виртуальном дереве.

**Как обрабатываются пробелы?** Кавычки объединяют строку в один
аргумент. Значение переменной также не разбивается по пробелам.
В одинарных кавычках подстановка переменных отключена.

**Что делает `chown -R`?** Меняет указанный узел и все пути с его
префиксом и разделителем `/`. Соседний каталог с похожим именем
не попадает в выборку. Права реальной ОС для этого не требуются.

**Чем отличаются `mkdir` и `mkdir -p`?** Обычная команда требует
существующего родителя и нового конечного каталога. `-p` создает
недостающих родителей и допускает уже существующий каталог.

**Нужны ли сторонние библиотеки?** Нет. Использованы `argparse`,
`xml.etree.ElementTree`, `base64`, `dataclasses`, `calendar`, `unittest`
и другие модули стандартной библиотеки Python.

**Что означает ошибка в тестовом сценарии?** Она может быть намеренной.
`stage4.shell` и `stage5.shell` должны возвращать 1; проверяющие скрипты
реальной ОС учитывают это и возвращают 0 при ожидаемом результате.

**Все ли особенности UNIX поддержаны?** Реализован учебный набор
команд и описанные режимы. Конвейеров, перенаправлений, запуска внешних
процессов, прав доступа и сохранения VFS на диск нет.

**Что будет при ошибке второго пути в `mkdir a b`?** Обработка идет
последовательно; успешное создание `a` сохраняется. Автоматического
отката нескольких изменений программа не выполняет.
